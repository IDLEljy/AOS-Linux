# AOS-Linux：从 Human-centric 到 Agent-centric 的智能体原生 Linux 内核设计

> **文档类型**：系统内核开发实施方案（由 AOS-Agent 开题报告升级）  
> **版本**：V1.1 · 2026-10-18（更新系统定位与长期路线）  
> **原则**：以 Agent 为一等系统服务对象，保留 Linux 与人类用户兼容；先完成可启动、可验证的内核改造，再逐步走向 Agent-centric；**暂不决定本地、云端或虚拟机的最终部署位置**。

---

## 0. 设计哲学：操作系统的服务对象正在变化

> **核心愿景**：从 **Human-centric OS（以人为主要服务对象）**，逐步演进为 **Agent-centric OS（以 AI Agent 为主要服务对象）**。**Agent-aware 是实现起点，Agent-native 是系统能力，Agent-centric 是长期方向。**

传统操作系统主要面向“人启动应用程序”，通过用户、进程、文件、权限等对象管理资源；面向 Agent 的工作负载则呈现**自主执行、跨工具、多进程、持续任务、频繁系统调用**等特点。

我们要把 **Agent 身份、Agent Task、任务状态、资源预算、能力边界与执行轨迹**提升为操作系统可理解、可观测、可控制的**一等系统语义**，并通过机器可读接口直接向 Agent 暴露必要的系统状态。这里的“一等”指**系统有原生管理语义和稳定接口**，不意味着 Agent 拥有高于人类用户的权限。

### 0.1 五项架构转变

| 维度 | 传统系统主要视角 | AOS-Linux 目标视角 |
|---|---|---|
| 服务对象 | 人类用户与应用程序 | 人类用户 + 以 Agent 为一等工作负载（长期向 Agent 优化） |
| 任务身份 | UID / PID / 进程组 | Agent ID → Task ID → cgroup / 进程树 |
| 资源管理 | 面向进程、容器和用户 | 面向 Agent 任务的预算、优先级、配额与服务质量 |
| 信息呈现 | Shell、GUI、通用系统监控 | 对 Agent 可理解的结构化状态、事件与能力描述 |
| 安全治理 | 用户、进程与文件权限 | 保留传统权限，并增加 Agent 任务级约束与审计 |

### 0.2 明确不采用的误区

- **不是固定把 70% 内存给 Agent、30% 给人类**：CPU、内存和 I/O 配额依据运行负载与策略动态调整，必要时保障交互式人类任务的最低响应能力。
- **不是让内核读懂自然语言或自行判断“任务完成了百分之几”**：内核报告真实进程/资源/安全事件；应用层 Agent 或任务框架报告业务里程碑和语义进度，再由 `aosd` 汇总。
- **不是让 Agent 具有 root 权限**：智能体可以成为系统优先服务的工作负载，同时始终受到明确授权、最小权限和隔离限制。
- **不是第一版就改写 Linux 调度器和全部系统调用**：先增加 Agent 原生语义和安全内核路径，随后用实验推动可验证的调度优化。

### 0.3 三步演进

1. **Agent-aware（第一阶段，课程 MVP）**：Linux 内核知道“哪个 Agent 的哪个任务”正在运行；可跟踪、约束、审计。
2. **Agent-native（第二阶段，完整作品）**：提供原生机器可读系统接口、结构化任务状态、受控操作能力与独立任务生命周期。
3. **Agent-centric（第三阶段，研究拓展）**：在保障系统安全和人类交互底线的前提下，研究对 Agent 工作负载更合适的资源分配、调度与多 Agent 协作。

## 1. 项目定位与最终目标

### 1.1 一句话定义

在**现有 Linux 内核源码**基础上，引入 **Agent ID / Agent Task** 等一等系统语义，并提供**内核级身份关联、安全控制、资源管理、事件审计**与**结构化 Agent 系统接口**，逐步实现从“主要面向人操作”到“优先适配 Agent 自主任务”的架构演进，最终形成可启动的 **AOS-Linux 定制 Linux 系统**。

### 1.2 与原开题报告的关系

原方案《AOS-Agent Agent-aware 操作系统交互与资源管理框架》包含五个模块：Task Manager、System API、Capability、Workspace、Audit；原方案明确“不重新实现 Kernel”，主要做用户态 OS Interaction Layer。本方案**保留这五项需求，但改变实现层次与目标**：把任务身份、关键访问控制、审计等核心机制下沉至内核，把 LLM、策略配置、交互页面留在用户态；进一步增加 **Agent 原生可观测接口** 与 **面向任务目标的资源管理策略**。

**注意**：这是“**基于 Linux 的内核改造与定制系统**”，不是从零编写 CPU 调度器、虚拟内存管理、驱动和文件系统的全新独立内核。课程答辩时应准确描述这一点。

### 1.3 可验收的最终成品

1. **AOS-Linux 内核源码**：包含实际修改、可追踪的补丁和编译配置。
2. **可启动的定制系统**：启动后能证明当前运行的是包含 AOS 功能的自编译 Linux 内核。
3. **AOS 内核子系统**：真实保存 Agent Task 信息并完成访问控制、审计等内核侧工作。
4. **`aosd` 用户态守护进程与 `aosctl` CLI**：负责注册任务、下发策略、查询状态、回收资源；对 Agent 提供稳定的机器可读接口。
5. **Agent 演示程序**：完成“读取代码→修改→测试→输出”，演示被内核阻断的越界访问。
6. **测试与实验报告**：功能正确性、权限绕过测试、性能开销、资源回收、复现实验。
7. **系统发布件**：完整可启动虚拟磁盘镜像/构建脚本；ISO 安装镜像属于可选扩展，不作为第一阶段硬性目标。
8. **Agent 原生观察能力**：通过结构化 JSON/API 查询 `agent_id`、`task_id`、子进程、资源预算、权限、生命周期、审计摘要；区分 OS 可观测状态与应用报告的任务进度。

## 2. 技术路线决策

### 2.1 核心路线

> **修改 Linux 内核源码（in-tree） + Agent Task 核心语义 + 原生 LSM 安全钩子 + 现有 cgroup v2 / Namespace + Agent 原生 API + 用户态 Agent 服务。**

采用“**内核核心机制 + 用户态策略编排**”的分层结构，使 Agent 成为 OS 能识别和控制的工作负载。内核必须独立于 LLM 工作，不能在内核中调用模型 API、运行 Python 或解析复杂自然语言。

```text
┌──────────────────────────────────────────────────────────┐
│ AI Agent / LLM                                            │
│ 自主规划、选择工具、请求执行                               │
└──────────────────────────┬───────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────┐
│ 用户态 AOS Control Plane                                 │
│ aosd 守护进程 · aosctl 命令行 · Agent 原生状态 API         │
│ 策略 / Workspace · 任务进度上报 · 资源统计 · 审计导出       │
└──────────────────────────┬───────────────────────────────┘
                           │ /dev/aosctl (ioctl) / tracefs
┌──────────────────────────▼───────────────────────────────┐
│ AOS-Linux：修改后的 Linux Kernel                          │
│ ┌─────────────┐ ┌─────────────┐ ┌──────────────────────┐ │
│ │ Agent Task  │ │ Agent LSM   │ │ Audit / Trace Events │ │
│ │ 身份与状态   │ │ 强制访问控制 │ │ 内核事件与资源标签    │ │
│ └─────────────┘ └─────────────┘ └──────────────────────┘ │
│      cgroup v2     Namespace / VFS    Linux Process      │
└──────────────────────────────────────────────────────────┘
```

### 2.2 为什么不直接修改 `task_struct` 和调度器？

- **第一阶段不修改 `task_struct`**，优先以 **cgroup ID / cgroup 归属**关联 `task_id`。进程及其子进程天然继承 cgroup 归属，能够表达“一个 Agent 任务对应一组进程”。
- **第一阶段不改 CFS/EEVDF 调度算法**。CPU、内存、进程数配额直接使用 Linux cgroup v2；我们的创新重点是**Agent 任务语义和端到端受控执行**。后续是否引入 Agent-aware 调度策略，取决于实测瓶颈而非概念需要。
- **不硬切内存或 CPU 给人类和 Agent**。首版采用任务限额、相对权重和人类交互任务保护策略，做到可调整、可观察、可回滚。
- 必须明确：**调用 cgroup/Namespace 本身不是内核源码创新**；创新代码集中在新增 Task Registry、Agent LSM、策略与内核审计机制。

### 2.3 BPF LSM 与原生 LSM 的关系

- **快速试验路径**：当目标内核支持并启用了 BPF LSM 时，可先通过 eBPF 试验 `exec` / 文件访问安全钩子，尽早验证策略是否合理。
- **最终集成路径**：在 Linux 源码树内新增 **in-tree 原生 LSM**，通过内核配置编译集成，并在启动配置中启用。原生 LSM **不能当作普通 `.ko` 模块随意热插拔**，不能混淆两者。
- 如果 BPF LSM 不可用，**不应将仅有 Python 层拦截的演示宣称为“内核安全拦截”**；应进入自编译内核的原生 LSM 路线。

## 3. 功能模块设计

| 模块 | 位置 | 必须实现的最小功能 | 预期可见效果 |
|---|---|---|---|
| **Agent Task Core** | 自研内核代码 | 创建/查找/销毁 `task_id`；与任务 cgroup 绑定；任务状态 | 内核能回答“这些进程属于哪个 Agent Task” |
| **Agent Security / Capability** | 自研原生 LSM | 对受控任务检查程序执行和文件访问 | 在直接系统调用路径拒绝越界行为，而不仅是 CLI 拒绝 |
| **Agent Resource** | Linux cgroup v2 + `aosd` | CPU、内存、进程数配额；任务权重、异常终止与回收 | Agent 工作负载受到预算管理，人类交互仍可响应 |
| **Agent Workspace** | Mount Namespace + 文件系统 + `aosd` | 独立工作目录；限定可读/可写范围 | 各任务工作区分离，结束后归档输出并清理 |
| **Agent Audit** | 内核事件 + `aosd` | 记录 Task ID、操作、结果、时间；导出日志 | 可追溯允许与拒绝的关键动作 |
| **System API / Agent Observation** | 内核控制接口 + `aosd` 结构化 API | 注册、配置、查询、终止任务；观察资源、事件、策略 | Agent 可直接读取结构化系统状态，而非解析 `ps` 文本 |

### 3.1 Agent Task Core（第一创新核心）

建议任务记录的逻辑字段：

```c
struct aos_task_info {
    __u64 agent_id;       /* Agent 身份标识（由可信管理层映射） */
    __u64 task_id;        /* AOS 任务唯一标识 */
    __u64 cgroup_id;      /* Linux cgroup 归属 */
    __u32 policy_id;      /* 生效策略编号 */
    __u32 state;          /* CREATED / RUNNING / STOPPING / FINISHED */
    __u32 qos_class;      /* 系统调度/服务等级（非绝对优先权） */
    __u64 created_ns;     /* 创建时间 */
};
```

> 上面是**逻辑示例，不是已经可直接编译的最终 ABI**。并发读写、引用计数、生命周期与具体 `cgroup_id` 获取方式，需要在固定 Linux 内核版本后实现。

设计要点：

- 一个 Agent 可以创建多个 Agent Task；一个 Agent Task 又可以关联多个进程、工具调用和文件产物；`Agent ID ≠ Task ID ≠ PID`。
- 任务的子进程继承所属 cgroup，避免仅靠最初 PID 管理导致子进程漏管。
- 任务注册由受信任的 `aosd` 完成，普通 Agent 不能自己注册为高权限任务或修改策略。
- 内核映射的读写需要处理并发和销毁过程中的对象有效性；优先使用成熟内核同步机制，不设计无锁算法作为 MVP。
- 任务结束时撤销权限关联，内核清理元数据；进程终止和目录归档由用户态协调。
- `qos_class` 表示管理层经过授权的服务等级；不可根据 Agent 自报“重要”就赋予最高级别。业务完成百分比不存进内核核心对象。

### 3.2 Agent Security（第二创新核心）

建立 **Capability Profile（允许操作 + 资源作用域 + 风险条件）**：

| 操作 | MVP 规则 |
|---|---|
| 读取项目文件 | 允许指定只读目录 |
| 写入代码和输出 | 仅允许任务工作区的可写区域 |
| 执行程序 | 允许预先批准的解释器、编译器和测试工具 |
| 访问系统敏感文件 | 拒绝，记录审计事件 |
| `sudo`、修改策略、管理其他任务 | 拒绝受控 Agent，自主执行不授予管理员权限 |
| 网络访问 | 首版默认关闭或通过隔离命名空间限制；细粒度域名白名单放入后续版本 |

最低限度覆盖两类内核级拦截：

1. **程序执行**：选择适合目标内核版本的 `bprm_*` 安全钩子，在真正执行前做策略检查。
2. **文件访问**：选择适合目标内核版本的 `file_open`、`inode_permission` 等钩子组合，根据访问场景验证读写权限。

**安全边界**：不能仅根据路径字符串判断 `path.startswith('/workspace')`，必须考虑符号链接、硬链接、bind mount、目录穿越和文件描述符继承。第一版采用 **Mount Namespace 最小暴露 + LSM 检查 + 非特权运行**，并对所有常见绕过方式做负向测试。不能向 Agent 提供宿主系统的 root、任意内核模块加载和策略管理权限。

### 3.3 资源管理

每个任务对应一个 cgroup v2 子树，由 `aosd` 配置：

```text
/aos/tasks/<task_id>/
  cpu.max       # CPU 配额
  memory.max    # 内存上限
  pids.max      # 可创建进程数量上限
  cgroup.procs  # 当前关联进程
```

说明：实际操作路径以 cgroup 挂载点和可写委派范围为准；必要时由 systemd 管理对应 slice/scope。资源统计应同时展示 `cpu.stat`、`memory.current`、`memory.events` 等指标。

**Agent-centric 资源策略不是固定占比**：首版使用 `cpu.weight`、`cpu.max`、`memory.high`、`memory.max`、`pids.max` 等现有接口实现不同任务的可控配额。若要保护交互服务，可为其单独设置合适的 cgroup 和限制/保护策略；使用 `memory.low`、`memory.min` 等内存保护时必须权衡总量与 OOM 风险。长期再探索基于任务截止时间、交互延迟和实际资源使用的动态调整算法。

### 3.4 Workspace 与审计

任务目录沿用原开题报告：

```text
workspace/task_<id>/
  input/        # 输入资料（按需只读挂载）
  working/      # Agent 可写工作区
  output/       # 交付结果
  logs/         # 任务日志
```

- 审计事件从**内核检查/执行路径**产生，再由 `aosd` 接收、落盘为 JSONL；失败、拒绝、资源超限也应记录。
- MVP 可优先使用内核 tracepoint/tracefs 输出结构化事件，后续再增加专用事件通道。不得把 Python 自己打印的日志冒充为内核审计。
- 日志最低字段：`timestamp`、`task_id`、`pid`、`action`、`target`、`decision`、`errno`、`policy_id`。
- **允许日志丢失时要显式记录丢失计数**；若审计属于强安全要求，则需另行设计可靠性与阻断策略。

### 3.5 Agent 原生状态与上下文接口（新增）

让 Agent “看得懂系统”，不等于给内核对象随意加字符串标签；应建立**明确语义的结构化视图**：

| 数据类型 | 负责提供 | 示例 |
|---|---|---|
| Agent / Task 身份 | AOS Task Core | `agent_id`、`task_id`、`state`、`policy_id` |
| 进程与资源事实 | Linux 内核 + cgroup | 子进程、CPU/内存使用、资源上限、OOM 事件 |
| 安全与行为事件 | AOS LSM / Audit | 操作类型、允许/拒绝、错误码、时间戳 |
| 任务语义进度 | 用户态 Agent / 任务框架 | `step=testing`、`completed_steps=3/5`、`last_result` |
| 可执行能力目录 | 可信策略管理器 | 允许使用的工具、允许访问的作用域 |

`aosd` 合并内核事实与经校验的用户态进度，提供版本化、只读的 JSON/API。Agent 可以查询“任务正在执行什么进程、耗费多少资源、下一步是否可执行”，但**不得借观察接口直接修改内核状态或提升权限**。

示意响应（仅表示接口方向，不等于已实现）：

```json
{
  "agent_id": 42,
  "task_id": 7,
  "state": "RUNNING",
  "resource": {"memory_bytes": 104857600, "memory_limit_bytes": 536870912},
  "process_count": 3,
  "capabilities": ["file.read:project", "file.write:working", "exec:python"],
  "progress": {"source": "agent_report", "stage": "testing", "completed_steps": 3, "total_steps": 5}
}
```

**设计约束**：业务进度来自 Agent 上报，不是内核自行推断；监控 API 必须认证授权，避免跨 Agent 泄漏进程、文件路径及日志细节。

## 4. 内核改造范围与代码结构

建议在固定版本的 Linux 源码树中新增相对独立的目录，尽量减少对原有模块的侵入：

```text
AOS-Linux/
├── linux/                         # 固定版本的 Linux 内核源码
│   └── security/aos/              # 自研 AOS 内核组件（建议组织形式）
│       ├── Kconfig
│       ├── Makefile
│       ├── aos_task.c              # Task ID / cgroup 身份映射
│       ├── aos_policy.c            # 策略表示和匹配
│       ├── aos_lsm.c               # 原生 LSM hook 接入
│       ├── aos_control.c           # /dev/aosctl 内核控制接口
│       └── aos_audit.c             # 审计事件产生
├── include/uapi/linux/aos.h       # 用户态/内核态公共接口定义
├── userspace/
│   ├── aosd/                       # 受信任的控制守护进程 + 结构化状态 API
│   ├── aosctl/                     # CLI
│   ├── agent-demo/                 # LLM/工具调用、进度上报演示
│   └── dashboard/                  # 可选图形界面
├── policies/                       # 配置化权限策略
├── tests/
│   ├── kernel/                     # 内核功能测试
│   ├── security/                   # 绕过与越权测试
│   ├── resource/                   # CPU/内存/进程配额测试
│   └── e2e/                        # 端到端测试
├── scripts/                        # 构建、安装、测试、镜像脚本
├── docs/                           # 原理、接口、实验与报告
└── releases/                       # 可复现构建产物清单
```

> 真实主线 Linux 中的配置注册与初始化调用，需要按所选内核版本连接到 `security/Kconfig`、`security/Makefile`、LSM 注册体系等；此目录布局是**工程规划**，不是完成状态。

### 4.1 用户态—内核态接口

首版建议采用 `miscdevice` 暴露 `/dev/aosctl`，使用**带版本和长度字段的 ioctl 结构体**提供以下操作：

```text
AOS_TASK_CREATE     注册任务（由 aosd 完成）
AOS_TASK_BIND       绑定任务与预创建的 cgroup
AOS_POLICY_SET      下发策略（仅受信任管理员）
AOS_TASK_QUERY      查询任务身份与状态（敏感字段鉴权）
AOS_TASK_FINISH     设置结束状态并撤销任务关联
```

必须考虑：鉴权、用户指针校验、内存申请失败、并发、ABI 版本兼容和错误码。`aosctl` CLI 只与 `aosd` 通信，不让任意用户直接操作高权限 ioctl。

**Agent 原生状态查询由 `aosd` 提供版本化接口**，先不为每个查询新增内核系统调用；内核提供客观任务事实，`aosd` 汇总安全策略、资源视图与 Agent 上报的语义进度。

### 4.2 任务执行完整流程

```text
用户下达任务
  ↓
aosd 创建 workspace 与 cgroup
  ↓
注册 task_id / cgroup_id，装载策略
  ↓
以低权限身份创建 Agent 任务（先归组，再执行不可信程序）
  ↓
Agent 发起 file / exec / network 操作
  ↓
Linux 内核正常执行路径 → AOS LSM 检查
  ├── 允许：继续执行，记录审计
  └── 拒绝：返回 -EACCES / -EPERM，记录审计
  ↓
Agent 收集结果并上报语义进度 / aosd 汇总状态、审计和资源统计
  ↓
终止残留进程 → 保存 output 和 logs → 清理 workspace / cgroup
```

## 5. 分阶段实现计划与验收门槛

> 不以具体云平台或虚拟机作为技术前提；各阶段必须有**可观察输出和自动化测试**。时间为参考工作量，不代表已实现。

| 阶段 | 工作重点 | 必须提交的成果 | 通过条件 |
|---|---|---|---|
| **P0 基线** | 固定内核版本；建立编译、启动、回滚流程 | 可启动的未修改 Linux 内核与构建脚本 | 能识别内核版本、复现启动、保存启动日志 |
| **P1 内核身份** | 加入 AOS Kconfig、Task Registry、`/dev/aosctl` | 第一份实际内核源码补丁 + CLI | 注册任务、查询、销毁可重复运行，越权 ioctl 失败 |
| **P2 内核安全** | 加入原生 LSM，先管 `exec` 和文件访问 | 策略加载与允许/拒绝事件 | 直接进行系统调用仍被拦截，绕过测试通过 |
| **P3 资源与隔离** | cgroup v2、Workspace、进程清理 | 任务级 CPU/内存/pids 限制 | 资源超限可观测，任务结束无遗留进程，不破坏交互服务 |
| **P4 审计与可观测** | 内核事件 → `aosd` → 统一日志与状态 API | 包含 Agent/Task ID 的审计记录与 JSON 状态视图 | 允许、拒绝、异常可追踪；Agent 可读到资源和任务状态 |
| **P5 AI Agent** | 接入工具调用、修复代码的端到端任务 | 成功场景 + 越权场景 Demo | Agent 完成任务且无法绕开内核策略 |
| **P6 定制系统** | 构建可启动系统镜像与交付物 | 完整镜像、源码补丁、测试结果 | 全新环境可按说明启动系统并复现实验 |
| **P7 Agent-centric 优化（研究扩展）** | 动态任务配额、任务优先级、多 Agent 资源竞争实验 | 可关闭的实验策略 + 定量对照 | 对 Agent 效率有可测收益，同时守住人类交互、安全与公平基线 |

**最小可交付成品（MVP）**：P0～P4 + 一个不依赖大模型的脚本演示。  
**完整课程作品**：P0～P6，其中 P5 的模型可使用 API，不需要本地训练。  
**后续研究增强**：细粒度网络权限、多 Agent 协作、策略动态更新、Agent-aware 资源调度（需额外实验依据）。**P7 不属于第一阶段必须完成的课程 MVP。**

### 建议开发顺序：先做内核功能，再做 AI 界面

不要先花时间做聊天页面、Agent 框架和系统美化。最有价值的第一次演示是：**同一个未获授权的动作在普通 Linux 基线中可被执行，在 AOS 受控任务中由内核拒绝，并出现可验证的 Task ID 审计事件。**

## 6. 核心演示案例

### 场景 A：AI Agent 修复代码（原开题报告案例）

1. 用户要求“修复有 Bug 的代码并运行测试”。
2. `aosd` 为任务创建 `task_id=7`、工作区及资源配额。
3. Agent 读取允许的项目源码，在 `working/` 生成修复文件。
4. Agent 执行受允许的 `python`/编译器并运行测试。
5. 系统记录每次关键文件访问、执行结果和资源变化。
6. 输出测试报告到 `output/`，结束任务并清理其进程。

**验收**：功能正确、权限策略有效、最终产物和审计日志齐全。

### 场景 B：内核越权拦截（最关键演示）

让受控任务尝试读取一份**专门准备的禁止访问测试文件**，并通过另一个程序直接调用文件 API（不经过我们的 Python SDK）：

- 普通基线环境按照其原有权限策略运行。
- AOS-Linux 环境中，即使文件的常规 Unix 权限允许读取，AOS LSM 也应能基于任务策略拒绝访问。
- 返回拒绝错误，并输出包含 `task_id` 的内核审计事件。

同时验证符号链接、`../` 路径、重命名、继承文件描述符等情况，避免“只拦截演示脚本”的假安全。

### 场景 C：资源隔离

启动一个受控的 CPU 密集任务或内存占用任务，分别设置资源配额，观察其 CPU/内存限制是否按预期生效；完成后验证关联进程和临时资源已被回收。

### 场景 D：Agent 原生系统观察（新增）

Agent 通过 AOS 结构化 API 查询自己的任务身份、运行进程、内存预算、允许的动作、最近拒绝事件和用户态上报的任务阶段，验证这些字段与真实内核事件及 cgroup 统计一致。

### 场景 E：人类与 Agent 共存（研究扩展）

同时运行 CPU/内存密集型 Agent 和交互式人类服务，比较无策略、静态配额与动态策略下的 Agent 任务完成时间、交互响应延迟和资源开销；不得默认 Agent 优先抢占全部资源。

## 7. 实验设计与评价指标

| 实验问题 | 对照组 | AOS-Linux | 衡量方法 |
|---|---|---|---|
| 是否真正识别 Agent Task | 普通进程/PID 视角 | `agent_id` / `task_id` 与 cgroup/进程关联 | 任务关联正确率；子进程归属 |
| 是否能阻止越界操作 | 普通 Linux 权限基线 | 额外强制策略 | 允许/拒绝测试通过率；绕过率 |
| 是否能限制资源 | 无额外 Agent 配额 | cgroup 限额 | CPU 使用、内存峰值、进程数 |
| 是否可审计 | 普通程序日志 | 内核事件 + 任务关联日志 | 事件覆盖率、丢失数、可追溯率 |
| 额外性能成本多大 | 不加载 AOS 策略的同版本内核 | 启用 AOS 控制 | open/exec 延迟、吞吐变化、内存增量 |
| 能否清理任务 | 普通临时脚本 | 任务级退出与清理 | 残留进程/工作文件数量 |
| Agent 是否能理解系统状态 | 通用 `ps` / 人类可读命令 | Agent 原生 JSON 状态 + 事件摘要 | 字段完整性、更新延迟、正确率、越权不可见性 |
| 人类与 Agent 能否共存（P7） | 默认调度/无任务优先级策略 | 动态权重或配额策略 | Agent 完成时间、人类交互延迟、OOM 事件和公平性 |

**实验基本要求**：固定测试机配置、内核版本、输入规模，使用重复测量并报告中位数/均值和波动；不预先承诺某个性能提升百分比。安全模块的目标不是“让 CPU 更快”，而是提高任务控制一致性、隔离性和可审计性，并量化成本。P7 的资源策略必须与普通 Linux 及简单静态 cgroup 策略比较，避免把额外限制误称为调度优化。

## 8. 风险、边界与备选路线

| 风险 | 影响 | 应对 |
|---|---|---|
| 原生 LSM 无法直接作为普通可卸载模块 | 原型阶段改动成本提高 | 先用 BPF LSM 验证策略，再集成 in-tree 原生 LSM |
| Linux 内核 API 随版本变化 | 示例代码无法编译 | 固定内核源码版本、维护版本锁定和 CI 构建记录 |
| 内核崩溃 | 系统无法启动、丢失数据 | 在隔离测试环境启动、保留基线内核和回滚方案 |
| 用户态路径判断可绕过 | 安全性不成立 | Namespace、LSM、非特权执行，多种绕过测试 |
| 审计量太大 | 内存开销、丢事件 | 限制事件类型、批量写入、丢失计数 |
| 时间不足 | 定制系统不能按期交付 | P0～P4 作为第一优先级，UI、P7、多 Agent、ISO 后置 |
| 现有安全策略或 root 权限绕过 | 保护边界不清 | 明确威胁模型：**不把 root 当作不可信 Agent**，控制策略更新权限 |

**威胁模型**：防护目标是运行在非特权身份下、通过正常 Linux 内核接口执行操作的 Agent 任务；不宣称能防御已取得宿主机 root/内核执行权限的攻击者。为了避免任务在策略生效前运行，必须在执行不可信代码前完成 cgroup 归属和权限设置。

## 13. 版本变更说明（V1.0 → V1.1）

| 类别 | V1.0 | V1.1 |
|---|---|---|
| 项目定位 | Agent-aware 内核任务/安全管理 | **Human-centric → Agent-centric** 长期方向；Agent-aware 是第一阶段 |
| 管理对象 | Task ID | **Agent ID + Task ID** 两级身份及进程树关联 |
| 系统接口 | 内核管理 ioctl、审计 | **Agent 原生机器可读状态 API**，整合内核事实与用户态业务进度 |
| 资源观 | 任务限制和隔离 | **动态、可测的 Agent 任务资源策略**，不固定 Agent/人类内存比例 |
| 安全目标 | 内核级权限控制 | 保留原安全目标，强调 Agent 是一等工作负载**不等于拥有特权** |
| 演进路线 | P0～P6 | P0～P6 不变，新增 **P7 Agent-centric 实验优化**，不影响 MVP 交付 |

**定位表述建议（报告摘要可复用）：**

> AOS-Linux 面向 AI Agent 逐渐成为计算系统主要使用者的趋势，在现有 Linux 内核之上引入原生的 Agent 身份与任务语义，将任务级资源管理、权限控制、行为审计与结构化系统观察能力融入内核及其配套控制面。项目以 Agent-aware 内核扩展为可交付起点，逐步探索从 Human-centric OS 向 Agent-centric OS 的演进路径，并持续保留安全边界与人类用户兼容性。
